Ch.1 Introduction

  • Operating System: The software responsible for managing a computer's hardware and providing an API for user programs.

    • The operating system (OS) is responsible for allocating hardware resources, such as the CPU, memory, and I/O, to user programs.

  • A computer system can be divided into four components:

    1. Hardware: The computing resources of the system, including the CPU, memory, disk, and I/O devices.
    2. Operating System: The program that controls and allocates hardware resources to application programs. The operating system can be thought of a the program which provides an environment within which other programs can perform useful work.
    3. Application Programs: The programs that the user utilizes tho solve computing problems. Examples include word processors, web browsers, etc.
    4. User: The individual(s) that interacts with the system to perform work.

  • The role of the operating system can be explored from two views:

    1. User View: The role of the OS is to provide ease of use, as well as performance and security. The user is not concerned with resource utilization, that is, how various hardware/software resources are shared.
    2. System View: The role of the OS is to allocate resources to application programs. This involves managing conflicting requests for resources, and conducting the proper operation and control of I/O devices.

  • The OS is the one program running at all times on the computer, referred to as the kernel. Along with the kernel, there are two other types of programs:

    1. System Programs: Programs associated with the operating system, but are not part of the kernel. Also called daemons.
    2. Application/User Programs: All programs not associated with the operating system.

  • Mobile operating systems are designed for mobile devices such as phones or smart watches.

    • Mobile operating systems often provide middleware, that is, a set of software frameworks that provide additional services to application developers. This may include services to support databases, multimedia, or graphics.

  • A modern general-purpose computer consists of one or more CPUs, and a number of device controllers connected through a common bus that provides communication between components and Shared Memory.

    • Each device controller is in charge of a specific type of device. Depending on the controller, more than one device may be attached. A device controller maintains some local buffer storage and a set of special-purpose registers. The device controller is responsible for moving the data between the peripheral devices that it controls and its local buffer storage.
    • Typically, operating systems have a Device Driver for each device controller. This driver understands the device controller and provides the rest of the OS with a API to the device. The CPU and device controllers can execute in parallel, competing for memory cycles. A memory controller synchronizes access to the memory.

  • A device controller informs the device driver of some event via an Interrupt.

    • Hardware may trigger an interrupt at any time by sending a signal to the CPU, typically via the system bus. When the CPU is interrupted, it stops what it is doing and immediately transfers execution to a fixed location called the interrupt vector.
      • Each element in the interrupt vector is a pointer to an interrupt service routine (ISR). The ISR executes, and on completion, the CPU resumes the interrupted computation.
      • Computers may have more devices than they have address elements in the interrupt vector. A common way to address this issue is to use interrupt chaining, where each element in the interrupt vector points to the head of a list of interrupt handlers. When an interrupt is raised, the handlers on the corresponding list are called one-by-one until one is found that can service the request.
    • An alternative to an interrupt vector is to call a generic routine which then examines the interrupt information to call the correct interrupt-specific handler.
    • The interrupt architecture must also save the state information of whatever was interrupted, so that the state can be restored after the interrupt is serviced. If the interrupt routine needs to modify the processor state, it must explicitly save the current state and then restore that state before returning. After the interrupt is serviced, the saved return address is loaded into the program counter, and the interrupted computation resumes.
    • The CPU hardware has a wire called the interrupt-request line that the CPU senses after executing every instruction. When the CPU detects that a controller has asserted a signal on the interrupt-request line, it reads the interrupt number and jumps to the interrupt-handler routine by using that interrupt number as an index into the interrupt vector. It then starts execution at the address associated with that index. The handler saves any state it will be changing during its execution, determines the cause of the interrupt, performs the necessary processing, performs a state restore, and returns the CPU to the execution state prior to the interrupt.
    • We say that the device controller raises an interrupt by asserting a signal on the interrupt request line, the CPU catches the interrupt and dispatches it to the interrupt handler, and the handler clears the interrupt by servicing the device.
    • The basic interrupt mechanism just described enables the CPU to respond to asynchronous events. Though, a modern operating system requires more sophisticated interrupt-handling features, such as:
      • The ability to defer interrupt handling during critical processing.
      • An efficient way to dispatch to the proper interrupt handler for a device.
      • Multilevel interrupts, which allow the OS to distinguish between high and low priority interrupts, permitting the OS to respond with the appropriate degree of urgency. These levels of priority enable the CPU to defer the handling of low-priority interrupts without masking all interrupts and makes it possible for a high-priority interrupt to preempt the execution of a lower-priority interrupt.
    • In modern computer hardware, these features are provided by the CPU and the interrupt-controller hardware. Most CPUs have two interrupt request lines:
      1. Nonmaskable Interrupt: Interrupts that cannot be disabled/ignored. Typically reserved for critical events such as hardware failures or unrecoverable memory errors.
      2. Maskable Interrupt: Interrupts that can be ignored by the CPU before the execution of critical instruction sequences that must not be interrupted. Maskable interrupts are used by device controllers to request service.

  • The CPU can load instructions only from main memory (RAM), so any programs must be first brought into RAM to be eligible to run. Main memory is typically implemented as Dynamic Random-Access Memory (DRAM). DRAM is volatile, meaning it loses its contents when power is lost.

    • The first program to run on a computer is typically the bootstrap program, which then loads the operating system. The bootstrap program (and other forms of firmware), are stored in Electronically-Erasable Programmable Read-Only Memory (EEPROM).
    • The basic unit of computer storage is the bit. A bit can be either 0 or 1. A byte is 8 bits wide, and on many computers, the smallest convenient chunk of storage. A word is a given computer architecture's native unit of data. A kilobyte is 1,024 bytes; a megabyte is 1,024 bytes, etc.
    • All forms of memory provide an array of bytes, and each byte has its own address. Interaction is preformed via sequences of load and store instructions to specific memory addresses. The load instruction moves memory a byte or word from main memory to a CPU register. The store instruction moves the content of a CPU register into main memory. The CPU automatically loads instructions from main memory for execution from the address stored in the program counter.
    • Ideally we want the programs and data to reside in main memory permanently, though, this is not practical for two reasons:
      1. Main memory is usually too small to store all needed programs and data.
      2. Main memory is typically implemented as DRAM, which is volatile.
    • Because of these reasons, most computer systems include secondary storage as an extension of main memory. Secondary storage is typically much larger than main memory and is nonvolatile. The most common secondary storage devices are hard-disk drives (HDDs) and solid-state drives (SSDs).
      • Most programs are stored in secondary storage and loaded into main memory when needed.
      • Secondary storage is typically many orders of magnitude slower than main memory, hence, the proper management of secondary storage is critical to system performance.
    • Furthermore, tertiary storage is a type of data storage used for long-term archiving and backup of data. Tertiary storage is commonly implemented via magnetic tape or optical disks.
    • The wide variety of storage systems can be organized into a hierarchy called the memory hierarchy. The hierarchy is organized in such a way that smaller, faster memory is closer to the CPU, and memory gets increasingly larger and slower the further it is from the CPU.
      • Caches are used to improve the performance of the memory hierarchy by providing a buffer for slower devices. Caches are used to store frequently accessed (or soon-to-be accessed) data closer to the CPU, thereby improving memory access time.

  • A typical instruction-execution cycle first fetches an instruction from memory and stores the instruction in the instruction register. The instruction is then decoded to set the values of the control signals, and may cause operands to be fetched from memory and stored in some internal register. After the instruction on the operands is executed, the results may be stored back in memory.

  • A large portion of operating system code is dedicated to managing I/O (input/output). The interrupt-driven I/O described earlier is fine for moving small amounts of data but can produce high overhead when used for bulk data movement such as for nonvolatile storage (NVS) I/O. This problem can be solved using Direct Memory Access (DMA).

    • DMA allows certain hardware devices to access main memory independently, that is, with no intervention from the CPU. The device controller transfers an entire block of data directly to or from the device to main memory. Only one interrupt is generated per block to tell the device driver that the transfer is complete, rather than one interrupt per byte.

  • Historically, most computer systems consisted of a single processor containing one CPU with a single processing core. This is called a uniprocessor system.

    • A core is the individual processing unit within a CPU. A CPU is a type of processor which serves as the central processing unit for a computer.
    • Many computers also have special-purpose processors, such as GPUs or disk controllers.

  • Modern computers are typically multiprocessor systems. Such systems typically include a single CPU that is made up of two or more cores. Such a processor is called a multicore processor.

    • Alternatively, a computer can be made up of multiple single/multicore CPUs to form a multiprocessor system. Multicore multiprocessors are commonly cheaper, faster, and more power-efficient than multiple single-core processors. The speed improvement comes from the fact that on-chip communication is faster than inter-chip communication.
      • In a multicore chip, each core has its own register file, as well as its own L1 cache (level 1 cache). Many multicore processors also include a L2 and L3 cache which may be local to a core or shared across multiple cores.
      • A multicore processor with cores appears to the CPU as distinct processors. Adding additional processors will increase computing power, though other factors, such as bus contention or disk performance, can become a significant bottleneck.
      • Bus contention can be addressed by providing each CPU with its own local memory that is accessed via a small, fast local bus. Each CPU can also access the memory of other CPUs via a shared system interconnect, so that all CPUs share one physical address space. This type of system is called a Non-Uniform Memory Access (NUMA) system, since a processor has a faster access time to its local memory than to remote memory. NUMA systems are becoming increasingly popular due to their ability to efficiently scale to a large number of processors.
    • The most common multiprocessor systems use symmetric multiprocessing (SMP) where each processor performs all tasks, including operating system functions and user processes. Conversely, asymmetric multiprocessing systems designate different roles and responsibilities to each processor and are far less common.
      • In SMP Systems, processes can run simultaneously if there are CPUs. However, since the CPUs are separate, one may be sitting idle while another is overloaded, resulting in poor performance. This problem is called load imbalance.

  • Clustered systems consist of multiple independent computers called nodes, that are then connected via a high-speed network.

    • A popular appeal for clustered systems is their ability to provide high-availability service. This availability is obtained by running a cluster software that runs on the cluster nodes. This software is responsible for monitoring each node for failure. If a node fails, its tasks are migrated to other nodes. Such a system is called fault-tolerant, because it can suffer the failure of any single component and still continue operation.
    • Clustering can be conducted asymmetrically or symmetrically:
      • Asymmetric Clustering: One server is the active server which performs computations, while the other server is in hot-standby mode. The hot-standby machine monitors the active server and becomes the active server if it fails.
      • Symmetric Clustering: Each node is running applications and are monitoring each other.
    • Clusters are commonly used to provide high-performance computing for intense scientific or mathematical calculations. This involves a technique known as parallelization, which divides a program into separate components that run simultaneously on individual cores in a computer or computers in a cluster.

  • When a computer is turned on, the bootstrap program is responsible for loading the operating system. This program initializes all aspects of the system, including CPU registers, device controllers, and memory contents.

    • To load the operating system, the bootstrap program must locate the kernel on disk and load it into memory. Once the kernel is loaded and executing, it can start providing services to the system and users. Some services are provided through system programs outside of the kernel, called daemons.
    • An operating system responds to events, such as an interrupt signal. In addition to the already mentioned hardware interrupts, software-generated interrupts (called exceptions) can be caused by either an error or by a specific request from a user program that an operating system service be performed by executing a system call.
      • A system call is the mechanism through which application programs request services from the operating system kernel. These include services such as file management, process control, memory management, or device control.

  • One of the most important functions of modern operating systems is the ability to run multiple programs simultaneously. Such a system is referred to as a multiprogrammed system, where each program in execution is called a process.

    • In a multiprogrammed system, the OS keeps multiple processes in memory simultaneously and picks one to executed according to the CPU scheduler. The CPU scheduler the part of the kernel responsible for selecting which process to run on the CPU and for how long.
    • Multi-programming increases CPU utilization by organizing programs so that the CPU almost always has one to execute. If the current executing process blocks (due to an I/O operation or to wait for some signal), the operating system can switch to another process to execute.
    • Multitasking is the extension of multiprogramming, where the CPU executes multiple processes by quickly switching among them, providing the user with a fast response time.

  • A modern operating system needs some mechanism(s) to ensure that an incorrect or malicious program cannot cause harm to other programs or to the system.

    • Commonly, the operating system needs some mechanism to distinguish between the execution of system code and user code. This mechanism is provided by the hardware providing multiple modes of execution. We need at least two modes:
      1. User Mode: The execution mode that user applications run in. It has restricted access to system resources and hardware.
      2. Kernel Mode: The execution mode that the operating system runs in. It has full access to all system resources and hardware.
    • The mode bit is added to the hardware of the computer to indicate the current mode. When a user application wants to request a service from the operating system (via a system call), the system must transition from user mode to kernel mode. This operation is called a context switch.
    • Having multiple modes of execution enables us with the means for protecting the operating system from user programs. This is done by designating some of the machine instructions as priviledged instructions, meaning they can only be performed in kernel mode. If an attempt is made to perform a priviledged instruction in user mode, the hardware treats the instruction as illegal and traps it to the operating system.
      • System calls are the mechanism for user programs to request services from the operating system. A system call usually takes the form of a trap to a specific index in the interrupt vector. When a system call is executed, the hardware treats it as a software interrupt. Control passes through the interrupt vector to a service routine in the kernel, and the mode bit is set to kernel mode. A parameter indicates what service the user program is requesting. Additional information may be passed via pointers, registers, or on the stack. The kernel verifies the parameters are legal, executes the request on behalf of the user program, and returns control to the instruction following the system call.
      • If a user program attempts to perform an illegal instruction, the hardware traps to the OS and the trap transfers control through the interrupt vector, just as an interrupt does.
    • CPUs that support virtualization may have a separate mode to indicate when the virtual machine manager (VMM) is in control of the system. This mode typically has more privilege than user mode but less than kernel mode.

  • A timer is used to ensure that the OS maintains control over the CPU. Using a timer prevents a user program from running on a CPU indefinitely. The timer can be set to interrupt the computer after a specified period, fixed or variable. A variable timer is generally implemented as a fixed-timer and a counter.

  • A process is an instance of a program in execution. Processes need certain resources, including CPU time, memory, files, and I/O devices, to accomplish its task. These resources are typically allocated to the process by the kernel at runtime.

    • To be clear, a program by itself is not a process. A program is a passive entity, typically a file on disk. A process, on the other hand, is an active entity. Processes are the unit of work in a system.
    • A single-threaded process has a single program counter specifying the next instruction to execute. The execution of such a process must be sequential.
    • Although two processes may be instances of the same program, they are considered two separate execution sequences. A multithreaded process has multiple program counters, each pointing to the next instruction to execute for a given thread.
    • The OS is responsible for the following operations regarding processes:
      1. Creating and deleting processes.
      2. Scheduling processes and threads on the CPUs.
      3. Suspending and resuming processes.
      4. Providing mechanisms for process synchronization.
      5. Providing mechanisms for process communication.

  • Main memory is a large array of bytes, where each byte has its own address. Instructions must be in main memory for a CPU to be able to execute them.

    • To improve CPU utilization and response time, general-purpose computers must be able to keep multiple processes in memory simultaneously.
    • The OS is responsible for the following operations regarding memory management:
      1. Keeping track of which parts of memory are occupied and what process its occupied by.
      2. Allocating and deallocating memory as needed.
      3. Deciding which processes (or parts of processes) to move in and out of memory.

  • Most general-purpose operating systems provide a uniform, logical view of disk storage known as the file-system. The operating system abstracts the physical properties of storage devices to define a logical storage unit, called the file.

    • A file is a collection of related information defined by its creator. Files commonly represent programs or data. The OS implements the abstract concept of a file by managing mass storage media and the devices that control them. Furthermore, many operating systems provide directory structures to organize files.
    • The OS also commonly provides access control for files, which decides what users are allowed to access a file and how they may access it.
    • The OS is responsible for the following operations regarding file management:
      1. Creating and deleting files.
      2. Creating and deleting directories to organize files.
      3. Supporting primitives for manipulating files and directories.
      4. Mapping files onto mass storage.
      5. Backing up files onto tertiary storage.

  • A computer system must provide secondary storage to back up main memory. This secondary storage is commonly implemented with hard disk drives (HDDs) or flash memory.

    • Most programs are stored on these devices until loaded into main memory.
    • The OS is responsible for the following operations regarding secondary storage management:
      1. Mounting and unmounting.
      2. Free-space management.
      3. Storage allocation.
      4. Disk scheduling.
      5. Partitioning.
      6. Protection.
    • Because secondary storage is used so frequently, the entire speed of operation of a computer may depend on the speeds of the secondary storage subsystem.

  • Caching improves the performance of the memory hierarchy by providing a buffer for slower devices. Data that is frequently used can be copied into a small, fast memory close to the CPU (the cache), and when a piece of data is needed, the cache is checked first, potentially subverting the rest of the memory hierarchy.

    • Internal programmable registers act a high-speed cache for main memory. The programmer or the compiler implement the register allocation and register-replacement algorithms to determine what data is kept in registers.
    • Some caches are implemented totally in hardware, such as the instruction cache which stores the instructions expected to be executed next.
    • Because caches have limited size, cache management is a deeply important aspect of performance.
    • In a multiprocessor system, each CPU maintains its own L1 cache. In such a system, there may be many copies of a particular datum in multiple caches. Ensuring that each copy of the datum in each cache reflect the same value is called cache coherency.

  • The I/O subsystem of the OS is responsible for abstracting away the peculiarities of specific hardware devices.

    • The I/O subsystem consists of several components:
      1. A memory-management component that includes buffering, caching, and spooling.
      2. A general device-driver interface.
      3. Drivers for specific devices.

  • If a computer system has multiple users and allows the concurrent execution of multiple processes, then access to data must be regulated by the OS.

    • Protection is any mechanism for controlling the access of processes or users to the resources defined by a computer system.
    • Security is any mechanism for defending a system from internal and external attacks.
    • Protection and security require the system to be able to distinguish among all its users. Many operating systems maintain a list of usernames and associated user IDs.
    • In some circumstances, we may want to distinguish between sets of users rather than individual users. This is done by defining a group, and the set of users belonging to that group. The user's UID and GIDs are included in every associated process and thread.

  • Virtualization is a technology that makes it possible to create and manage virtual instances of entire computer systems. These instances are called virtual machines, and they appear to the user as independent physical computers, each running their own operating system.

    • Virtualization enables operating systems to operate as applications within other operating systems. A virtual machine manager (VMM), commonly known as a hypervisor, is the software layer responsible for managing these virtual machine instances.

  • Emulation involves simulating computer hardware in software. Every machine instruction that runs on the native system must be translated to the equivalent function on the target system, thus, incurring a severe performance overhead.

  • Distributed systems are collections of independent computers connected together via a high-speed network that work together to achieve a common goal.

  • A network is a communication medium between two or more components within a system, or between two or more systems. Networks vary by the protocols used, the distances between nodes, and the transport medium.

    • TCP/IP is the most common network protocol and the basis for the internet.
    • Networks are characterized based on the distances between nodes:
      • Local-Area Network (LAN): Connects computers within a building or campus.
      • Wide-Area Network(WAN): Connects buildings, cities, or countries together.
      • Metropolitan-Area Network (MAN): Links buildings within a city together.
      • Personal-Area Network(PAN): Links together multiple personal devices, such as a laptop, phone, and headset.
    • The physical medium that connect nodes include copper wire, fiber optic, wireless transmission between satellites, radios, etc.
    • A network operating system is an operating system that provides features such as file sharing across the network, along with communication schemes that allow processes across different computers to communicate with one another.

  • Common data structures that are used extensively in operating systems include:

    • Array: Consists of several elements that are accessed by their index.
    • List: Consists of several elements that are ordered and accessed sequentially.
      • A linked list implements a list by adding a pointer to each list element which points to the next element in the list.
      • In a doubly linked list, each element has a pointer to the list element before and the list element after it.
      • In a circularly linked list, the tail of the list points to the head of the list.
    • Stack: A sequentially ordered data structure that abides by the last in first out (LIFO) principle for adding and removing items. Adding and removing an item for a stack is referred to as a push and a pop, respectively.
    • Queue: A sequentially ordered data structure that abides by the first in first out (FIFO) principle for adding and removing elements.
    • Tree: A data structure that can represent hierarchical data. Nodes in a tree data structure are arranged according to a parent-child relationship. In a general tree, a node can have any number of children. In a binary tree, each node can have at most two children: a left child and a right child.
      • A Binary Search Tree is a binary tree where the value of the left child is less than or equal to the value of the right child for each node.
    • Hash Table: Computes the index of value in an associative array according to a hash function. This allows for a lookup time as good as .
      • Collisions occur when two values result in the same hash index. A common way to handle collisions is to have each index in the hash table be an array, an if an index already has a value in it, simply append the new value to the end of the array. This technique is called chaining.
    • Bitmap: A string of binary digits that can be used to represent the status of items. Bitmaps are used extensively in operating systems due to their space efficiency.

  • Operating systems exist for wide varieties of computing environments:

    • Traditional computing includes PCs connected to a network, and file and print servers. Popular operating systems for traditional computing include Linux and Windows.
    • Mobile computing includes handheld smartphones, tablets, and laptops. Augmented-reality hardware is another form of mobile computing. Popular operating systems for mobile computing include Apple iOS and Google's Android.
    • Client-server computing feature arrangements where server systems satisfy requests of client systems. Server systems are either:
      • Compute Servers: Provide computation services to clients.
      • File Servers: Provide a file-system interface for clients.
    • Peer-to-Peer Computing differs from the client-server model in the sense that each computer can act as both a client and a server simultaneously.
    • Cloud Computing is a model that delivers computing, storage, and applications as a service across a network.
    • Real-Time Embedded Systems are the most common types of computers. They are embedded within other objects that are not commonly thought of as computers; such as cars or washing machines. Operating systems for these environments typically provide little to no user interface.
      • Embedded operating systems are almost always real-time operating systems. A real-time system is an OS specifically designed to manage resources and run applications according to predictable and deterministic time constraints.

Ch.2 Operating-System Structures

  • An operating system provides an environment for the execution of programs.

  • One set of operating system services provides functions for the user:

    • User Interface: The means by which users interact with the system. Most modern operating systems offer a graphical user interface (GUI), where the interface is a window system with a mouse that serves as a pointing device. Alternatively, a command line interface (CLI) is a text-based interface where users type commands to perform tasks. Many mobile devices provide a touchscreen interface, enabling users to interact with the system with gestures.
    • Program Execution: The system must be able to load a program into memory and execute it.
    • I/O Operations: The system must provide the means to perform I/O operations since user programs typically do not have control to perform I/O directly.
    • File-System Manipulation: The OS must provide a file-system that can read, write, create, delete, search, and list files. A directory structure is commonly implemented to organize files into a hierarchy. Many operating systems provide permission management to control what users have access (and what sort of access) to what files.
    • Communication: The OS must provide means for inter-process communication (IPC), so that distinct processes within the same system have a means to communicate with one another. Communication may be implemented with shared memory, where two or more processes can read and write a shared section of memory, or message passing, where packets of information are moved between processes by the OS.
    • Error Detection: The OS needs to be constantly detecting and correction errors. Errors may occur in the CPU or memory hardware, in I/O devices (such as parity errors or connection failures on network devices), or in user programs (such as over/underflow or an illegal memory access). For each type of error, the OS should take the appropriate action to ensure correct and consistent computing.

  • Furthermore, another set of operating system services ensure the efficient operation of the system itself:

    • Resource Allocation: In a multiprogrammed system, resources must be appropriately allocated to each process. Resources include CPU time, memory, and file storage.
    • Logging/Accounting: The OS should keep track of what resources and how much resources each process utilizes.
    • Protection & Security: In a multiprogrammed system, it should not be possible for processes to access the memory of other processes unless they have been explicitly granted permission through mechanisms like shared memory. Security of the system from outside threats is also important. This includes password protection of user accounts, and defending external I/O devices, primarily network adapters, from malicious users.

  • As mentioned previously, a command-line interface (CLI) allows users to type in commands to perform operations on a system. Most modern operating systems treat the command interpreter as a special program that is running when a process is initiated or when a user first logs on.

    • On systems with multiple command interpreters, the interpreters are referred to as shells.
    • In one approach, the command interpreter itself contains the code to execute the command the user entered. Alternatively, commands can be implemented through system programs. In this case, the command interpreter uses the command to identify a file to be loaded into memory and executed. This allows for new commands to be appended to the system without having to recompile the interpreter itself, as well as keeping the interpreter size small.
    • Shell scripts are text files that contain a series of commands that are to be executed by a command interpreter. Shell scripts makes it easier to perform repetitive tasks by simply executing the shell script to perform the commands within it.

  • System calls are the interface to the services that an operating system provides. These calls are generally available as functions written in C/C++, though certain low-level tasks may have to be written in assembly language.

    • Application programmers design programs according to an application programming interface (API). The API specifies a set of functions that are available to the application programmer, including the parameters that are passed to each function and its return type. A programmer accesses an API via a library of code provided by the OS.
      • The functions that make up an API typically invoke the actual system calls on behalf of the application programmer. The benefits to utilizing an API rather than directly calling system calls include increased program portability. A program can theoretically run on any system that supports the same API that the program was written according to. Furthermore, actual system calls can be more difficult to work with than the API available to the application programmer.
      • Another important factor in handling system calls is the run-time environment (RTE), that is, the full suite of software needed to execute applications written in a given programming language, including compilers, interpreters, libraries, and loaders. The RTE provides a system-call interface that serves as the link to system calls made available by the OS. Typically, a number is associated with each system call, and the system-call interface maintains a table indexed according to those numbers. The system-call interface then invokes the intended system call in the operating-system kernel and returns the status of the system call.
    • System calls can be grouped into roughly six categories:
      1. Process Control: A running process needs to be able to halt its execution either normally (end()) or abnormally (abort()). There also needs to be system calls to create, load, and execute processes. Furthermore, system calls to get and set process attributes, wait and signal events, and allocate and free memory are required.
        • If a program is terminated abnormally, a dump of memory is sometimes taken (core dump), which can then be analyzed by a debugger.
        • An executing process may want to create and execute another program. If control is returned to the existing program when the new program terminates, we must save the memory image of the existing program. Furthermore, if both programs execute concurrently, we have created a new process to be multiprogrammed. Often there is a system call for this exact purpose (fork() in UNIX).
        • The exec() system call in UNIX takes an executable file as an argument, which then loads that program into the memory of the current processes.
        • Having created a new process, we may need to wait for them to finish their execution. Typically, we would wait for a specific event to occur, the child process should then signal when that event has occurred.
      2. File Management: System calls that can create, delete, open, close, read, write, and move files are essential. System calls that can get/set file attributes are also essential.
      3. Device Management: System calls to request, release, read, write, and attach/detach devices are needed; as well as system calls to get/set device attributes.
        • The similarities between I/O devices and files are significant, leading many operating systems to unify them into a combined structure known as the device structure. I/O devices may be identified by special file names, directory placement, or file attributes.
      4. Information Maintenance: System calls for getting/setting time and date, system data, and process/file/device attributes are required.
      5. Communication: System calls to create/delete communication connections, send/receive messages, transfer status information, and attach/remove remote devices are needed.
        • Often, processes may share data, therefore, system calls exist to lock shared data so that no other process can access it until the lock is released.
        • In the message-passing model, the communicating processes exchange messages with one another to transfer information. Messages can be exchanged between the processes directly or through a common mailbox. A connection must be established beforehand for communication to take place.
        • In the shared-memory model, processes use system calls to create and attach shared memory regions. This requires each process to agree to share its memory with the other processes. The processes are responsible for ensuring that they are not writing to the same location simultaneous, and the form of data being exchanged are determined entirely by the processes.
      6. Protection: System calls for getting/setting file permissions are needed.
    • Three general methods are used to pass parameters to the OS:
      1. The simplest approach is to pass parameters directly in registers.
      2. If there are more parameters than registers, parameters can be stored in memory, and the address of the block can be passed as a parameter in a register.
      3. Parameters can be pushed onto a stack by the program and popped off the stack by the OS.

  • System services/utilities are programs that are associated with the OS, though are not part of the kernel. They provide a convenient environment for program development and execution.

    • System services can be divided into the following categories:
      1. File Management: These programs provide services to access and manipulate files and directories.
      2. Status Information: Some programs simply ask the system for the date, amount of memory or disk space available, or other similar status information. More complex programs may provide detailed performance, logging, or debugging information.
      3. File Modification: Text editors may be available to create and modify the contents of files on disk.
      4. Programming Language Support: Compilers, assemblers, debuggers, and interpreters for common programming languages are often provided with the operating system.
      5. Loading and Execution: Loaders are responsible for loading an executable program into memory. The system may provide absolute loaders, relocatable loaders, linkage editors, and overlay loaders.
      6. Communication: These programs provide the mechanism for creating virtual connections between processes, users, and computer systems.
      7. Background Services: All general-purpose operating systems have methods for launching certain system program processes at boot time. Constantly running system program processes are known as daemons. Typical systems have dozens of daemons.

  • Many operating systems also supply application programs for performing common operations, including web browsers, text editors, email clients, etc.

  • Programs usually reside on disk as a binary executable file. To run on the CPU, the program must be loaded into main memory and placed in the context of a process.

    • Source files are compiled into object files that are designed to be loaded into any physical memory location, a format known as a relocatable object file. Next, the linker combines these object files into a single binary executable file. During this operation, other object files or libraries may be linked as well.
    • A loader is used to load the binary executable file into memory, where it is eligible to run on a CPU. Relocation is the process of assigning final addresses to the program parts and adjusting code and data in the program to reflect the final addresses.
    • Many systems allow programs to link to libraries at runtime, such libraries are called dynamically linked libraries (DLLs). The main benefit of such an approach is that if multiple processes link the same library, only a single copy of the library need be in memory, thus, reducing memory overhead. Furthermore, DLLs avoid linking and loading libraries that never get called during the execution of the program.
    • UNIX and Linux systems use the Executable and Linkable Format (ELF) file format for storing executable programs, object code, shared libraries, and core dumps. One critical piece of information in the ELF file for executable programs is the program's entry point, which contains the address of the first instruction to be executed.

  • Applications compiled on one operating system are typically not executable on other operating systems. This is because each operating system provides a unique set of system calls.

    • Applications can be made to run on multiple operating systems in the following ways:
      1. The application can be written in an interpreted language (such as Python) that has an interpreter available for multiple operating systems. The interpreter reads each line of the source code and executes equivalent instructions on the native instruction set and calls native system calls. This results in worse performance due to the overhead of the interpretation.
      2. The application can be written in a language that includes a virtual machine containing the running application. The virtual machine is part of the language's RTE. One such language is Java.
      3. The application programmer can use a standard language or API (such as the POSIX API) in which the compiler generates binaries in a machine and operating system specific language. The application must then be ported to each operating system explicitly.
    • The general lack of application mobility between operating systems has several causes which still makes developing cross-platform applications challenging, such as:
      1. The libraries provided with the OS contain APIs to provide services, therefore, an application designed to call one set of APIs will not be compatible with an OS that does not provide those APIs.
      2. Each operating system has a binary format for applications that dictates the layout of the header, instructions, and variables.
      3. CPUs have varying instruction set architectures (ISAs), and only applications containing the appropriate instructions can execute correctly.
      4. Operating systems provide system calls that allow applications to request various services (such as file manipulation). Those systems calls vary among operating systems in many ways, such as operands and return types.
    • At the architecture level, an application binary interface (ABI) is used to define how different components of binary code can interface for a given operating system on a given architecture. The ABI specifies low-level details, such a address width, how parameters are passed to system calls, the organization of the runtime stack, the size of data types, etc. Thus, an ABI is the architectural equivalent of an API.

  • When designing an operating system, various challenges will arise. However, there are proven strategies that can effectively address these issues.

    • The first problem in designing a system is to define goals and specifications. At the highest level, the design of the system will be affected by the choice of hardware and type of system: desktop/laptop, embedded, distributed, etc.
    • The requirements of the system may be much harder to specify. Requirements can be divided into two major groups:
      1. User Goals: The system should be convenient to use, secure, reliable, and fast.
      2. System Goals: The system should be efficient, fast, scalable, flexible, and easy to maintain.
    • One important principle when designing an OS is the separation of policy from mechanism. Mechanism determines how something is done, policy determines what should be done. This is a key principle for designing flexible systems, since policies are likely to change over time and place. A general mechanism that is flexible enough to work across a wide range of policies is more desirable than a strict one. A change in policy can therefore be implemented by a simple redefinition of certain parameters in the system.
    • Once an OS has been designed, it must be implemented. Most modern operating systems are written in C/C++, with small amounts of the system written in assembly language.
      • Utilizing a higher-level language like C/C++ for implementing operating systems results in code that is written faster, is more compact, and is easier to debug. Furthermore, advances in compiler technology result in code that is nearly as fast as code written directly in assembly. Finally, an OS written in a higher-level language is far easier to port to other hardware.
      • Although operating systems are large, only a small amount of code is critical to high performance; the interrupt handlers, I/O manager, memory manager, and CPU scheduler are the most critical routines.
    • A common approach for implementing operating systems is to partition the task into smaller components, rather than having one single system. Each of these modules should have well-defined interfaces and functions.
    • The simplest structure for organizing an operating system is to place all the functionality of the kernel into a single, static binary file that runs in a single address space. This is known as a tightly-coupled system because changes in one part of the system can have effects on other parts of the system. This approach is known as a monolithic structure, and is used by many operating systems include UNIX and Windows.
      • Monolithic kernels are difficult to implement, maintain, and extend. Though, they do have a distinct performance advantage since there is little overhead in the system-call interface.
    • Alternatively, a loosely-coupled system is divided into several smaller components that have specific and limited functionality.
      • A system can be made modular through various methods, one of which is the layered approach. In this approach, each layer is allowed to interact only with the layers beneath it. Each successive layer simplifies or abstracts the complexities of the layer below. Layered systems have been successfully used in computer networks and web applications, though, few operating systems use a pure layered approach. This is because of difficulties defining the responsibilities of each layer, as well as higher overhead resulting in poorer performance.
    • Microkernels are a type of operating system where all nonessential components are removed from the kernel and implemented as user programs in separate address spaces. This results in a much smaller kernel. The functions that are commonly retained in the microkernel include hardware management, inter-process communication (IPC), process management, and memory management.
      • One benefit of microkernels is that it is easy to extend the functionality of the system by simply adding a new service in user space, without needing to modify the kernel at all. This results in an OS that is easier to port to different hardware architectures. Furthermore, microkernels are more secure than traditional operating systems, since most services are running as user-level programs.
      • The performance of microkernels suffer due to increased system-function overhead.
    • Modern implementations of Linux, UNIX, and Windows use a technology known as loadable kernel modules (LKMs). Here, the kernel has a set of core components and can link in additional services via modules either at boot-time or runtime.
      • This approach represents a fusion of the monolithic and structured approach, since the kernel provides core services, and other services can be implemented dynamically. This makes it possible to add features to the kernel without having to recompile. Furthermore, this approach is more flexible than a layered system, since any module can call any other module.
        • LKMs can also be removed from the kernel when no longer needed, thus, increasing memory efficiency.
        • Linux uses LKMs primarily for supporting device drivers and file systems.
    • In practice, most operating systems combine different structures, resulting in hybrid systems.

  • Commonly, operating systems are designed to to run on any class of machines with a variety of peripheral configurations.

    • To build an OS from scratch, the following steps must be followed:
      1. Write the OS source code.
      2. Configure the OS for the system on which it will run. This involves specifying what features will be included. Commonly, parameters describing how the system is configured is stored in a configuration file of some type.
      3. Compile the OS.
      4. Install the OS.
      5. Boot the computer with the new OS.

  • Booting is the process of starting a computer by loading the kernel.

    • Commonly, the boot process follows these steps:
      1. A small piece of the code called the bootstrap program or boot loader locates the kernel.
      2. The kernel is loaded into memory and started.
      3. The kernel initializes hardware.
      4. The root file system is mounted.
    • Some computers use a multistage boot process:
      • When the computer is powered on, a small boot loader located in nonvolatile firmware known as the BIOS is run. The initial boot loader loads a second boot loader, which is located at a fixed disk location called the boot block. The program in the boot block may be sophisticated enough to load the entire OS into memory and begin its execution. Typically, though, it is simple code and knows only the address on disk and the length of the remainder of the bootstrap program.
    • Many modern computers have replaced the BIOS-based boot process with Unified Extensible Firmware Interface (UEFI). The main advantage of UEFI is that it is a single, complete boot manager and is therefore faster than a multistage boot process.
    • In addition to loading the kernel into memory, the bootstrap program may also run diagnostics to determine the state of the system. Furthermore, the bootstrap can also initialize all aspects of the system, including CPU registers, device controllers, and the contents of main memory. Eventually, it starts the OS and mounts the root file system. At that point, the system is said to be running.
    • GRUB is an open-source bootstrap program for Linux and UNIX systems.

  • Debugging is the process of finding and fixing errors in a system, both in hardware and software. Performance problems are considered bugs, so debugging commonly includes performance tuning.

    • If a process fails, most operating systems write the error information to a log file to alert users that a problem occurred. The OS may also take a core dump, that is, a snapshot of the memory of the process at the time of failure, and store it in a file for later analysis.
    • A failure in the kernel is called a crash, and the memory state at the time of the crash is saved to a crash dump.
    • A common problem in performance tuning is removing bottlenecks. To identify bottlenecks, we must be able to monitor system performance. Tools may be characterized as providing either per-process or system-wide observations. To make these observations, tools use one of two approaches:
      1. Counters: Systems keep track of system activity through a number of counters, such as the number of system calls made.
      2. Tracing: Collect data for a specific event, such as the steps involved in a system call invocation.
    • BCC is a toolkit for dynamic kernel tracing in Linux.

Ch.3 Processes

  • Early computers allowed only one program to be executed at a time. Modern systems are multiprogrammed, meaning multiple programs can be loaded into memory and executed concurrently.

    • Early systems were batch systems that executed jobs, followed by time-shared systems that ran user programs.
    • A process is a program in execution, and is the unit of work in a modern system. The status of the current activity of a process is represented by the value of the program counter and the content's of the processors registers.
    • The memory layout of a process is typically divided into multiple sections:
      • Text (fixed): The executable code.
      • Data (fixed): Global variables.
      • Heap (dynamic): Memory that is dynamically allocated during runtime.
      • Stack (dynamic): Temporary data storage when invoking functions, such as function parameters, return addresses, and local variables. Each time a function is called, an activation record containing function parameters, local variables, and the return address are is pushed onto the stack. When control is returned from the function, the activation record is popped from the stack.
    • The stack and the heap grow towards one another, with the heap growing upward, and the stack growing downward. The OS must ensure that they don't overlap one another.
    • A processes may be an execution environment for other code, for example, the Java Virtual Machine (JVM).
    • An I/O bound-process is one that spends more than doing I/O than performing computations. Alternatively, a CPU-bound process spends most of its time doing computations.
    • As a process executes, it changes state. The state of a process is defined in part by the current activity of that process. Processes are in one of the following states:
      1. New: The process is being created.
      2. Running: Instructions are being executed.
      3. Waiting: The process is waiting for some event, such as an I/O completion or a signal.
      4. Ready: The process is ready to be scheduled by the CPU scheduler.
      5. Terminated: The process has finished execution.
    • A processes is represented in the OS by its Process Control Block (PCB). It contains the following fields:
      1. Process State: The current state of the process.
      2. Program Counter: The address of the next instruction to be executed.
      3. CPU Registers: The values of all CPU registers.
      4. CPU-Scheduling Info: Scheduling priority, pointers to scheduling queues, and any other scheduling parameters.
      5. Memory-Management Info: Items such as the value of the base and limit registers and the page tables, or the segment tables, depending on the memory system used by the OS.
      6. Accounting Info: Items such as the amount of CPU cycles and real time consumed, time limits, account numbers, etc.
      7. I/O Status Info: The list of I/O devices allocated to the process, a list of open files, etc.
    • Most modern operating systems have extended the process concept to allow a process to have multiple threads of execution, and thus, perform multiple tasks simultaneously. This is especially beneficial on multicore systems, where multiple threads can run in parallel.
      • On systems that support multithreading, the PCB is expended to include information for each thread.

  • The process scheduler selects an available process (a process in the ready state) for program execution on a core. Each CPU core can run one process at a time. If there are more processes than cores, excess processes will have to wait until a core is free and can be rescheduled.

    • The number of programs currently in memory is referred to as the degree of multiprogramming.
    • As processes enter the system, they are put into a ready queue, where they wait to be scheduled onto a core. When a process is selected for execution by the CPU scheduler, it is said to be dispatched. The queue is generally implemented as a linked list.
    • Processes that are waiting for an event to occur, such as completion of I/O or a signal, are placed in the wait queue.
    • Once a process is dispatched to a processor, one of several things can happen:
      • The process could issue an I/O request and then be placed onto the wait queue.
      • The process could create a new child process and then be placed in a wait queue until the child's termination.
      • The process can be forcibly removed from the core, as a result of an interrupt or having its time quantum expire, and be put back onto the ready queue.
    • The responsibility of the CPU scheduler is to select a process from the ready queue to execute.
    • Some operating systems have an intermediate form of scheduling called swapping, where entire processes are removed from memory and into disk, thus, reducing the degree of multiprogramming. Later, the process can be reintroduced into memory and its execution can continue.
      • Swapping is typically only necessary when memory has been overcommited and must be freed up.
    • Interrupts cause the operating system to change a CPU core from its current task to run a kernel routine. When an interrupt occurs, the system needs to save the current context of the running processes so that it can be restored when its given the CPU back. The context is represented in the process's PCB.
      • We perform a state save of the current state of the CPU core, and a state restore to resume operations.
    • Switching the CPU core to another process is called a context switch. Context switch time is pure overhead, because the system does no useful work while switching.
      • Advanced memory-management techniques may require that extra data be switched with each context. For example, the address space of the current process must be preserved as the space of the next task is prepared for use.

  • A process may create several new processes. The creating process is called the parent process, and any processes it may create are called children processes.

    • Most operating systems identify processes according to a unique process identifier (PID), which is typically an integer.
    • A child process may be able to obtain its resources directly from the OS, or it may be constrained to a subset of the resources of its parent. Restricting a child process to a subset of the parent's resources prevents any process from overloading the system by creating too many child processes. Furthermore, the parent may pass along initialization data to the child process.
    • When a process creates a child, two possibilities exist for execution:
      1. The parent continues to executed concurrently with its child.
      2. The parent waits until some or all of its children have terminated.
    • There are also two address-space possibilities for the new process:
      1. The child process is a duplicate of the parent.
      2. The child process has a new program loaded into it.
    • In UNIX systems, the fork() system call creates a new process. The new process is a copy of the address space of the original process.
      • After the fork() call, one of the two processes typically use the exec() system call to replace the process's memory space with a new program.
      • The parent process can execute a wait() system call to move itself off the ready queue until the termination of its child.
      • The child inherits privileges and scheduling attributes from the parent, as well as certain resources, like open files.

  • A process terminates when it finishes executing its final instruction and asks the operating system to delete it using the exit() system call. Typically, the process returns a status value (integer) to its waiting parent process (via the wait() system call). All the resources allocated to the process are deallocated and reclaimed by the OS.

    • Termination can occur in other circumstances as well. A process can cause the termination of another process via an appropriate system call. Usually, such a call can only be invoked by the parent of the process to be terminated.
    • Some systems don't allow a child to exist if its parent has terminated. In such systems, when a parent process terminates, the OS also terminates all of its children, a technique referred to as cascading termination.
    • A parent process may wait for the termination of one of its children using the wait() system call. The wait system call is passed a int pointer that allows the parent to obtain the exit status of the child. Furthermore, the wait() call returns the PID of the terminated child so the parent can tell which of its children has terminated.
      • When a process terminates, all of its resources are deallocated by the OS. However, its entry in the process table must remain until the parent calls wait(), because the process table contains the process's exit status. A process that has terminated, but whose parent has yet to call wait() is called a zombie process. Once the parent calls wait(), the PID of the zombie process and its entry in the process table are released.
      • If a parent did not call wait() and instead terminated, it would leave its children as orphan processes. Traditional UNIX systems would handle this by assigning the init process as the new parent to the orphan processes. The init process would then periodically call wait(), thereby releasing the PIDs and process table entries of the orphans.
    • Because of resource constraints, mobile operating systems may have to terminate existing processes to reclaim resources. Rather than terminating an arbitrary process, Android has an importance hierarchy of processes, and if the system must terminate some process to free resources, it does so in order of increasing importance.

  • Processes executing in the system may be either independent processes or cooperating processes.

    • An independent process does not share data with any other processes in the system. A cooperating process can affect or be affected by other processes executing in the system.
    • There are several reasons for an operating system to support process cooperation:
      1. Information Sharing: Since several applications may be interested in the same information, we must provide an environment to allow concurrent access to such information.
      2. Computation Speedup: If we want a particular task to run faster, we could break it into multiple subtasks, each of which can execute in parallel with one another. Such a speedup can only be achieved in a system with multiple processing cores.
      3. Modularity: We may want to construct the system in modular fashion, dividing the system functions into separate processes or threads.
    • Cooperating processes require interprocess communication (IPC) mechanisms that will allow them to exchange data. There are two fundamental models of IPC:
      1. Shared Memory: A region of memory is shared by the cooperating processes. Can be faster than message passing since message passing typically requires the invocation of system calls. Shared memory, on the other hand, only performs system calls to establish a shared memory region. Afterwards, all reads and writes are treated as normal memory accesses.
        • Typically, a shared memory region resides in the address space of the process creating the shared memory segment. Other processes that wish to communicate using this shared memory segment must attach it to their address space.
      2. Message Passing: Messages are explicitly sent between cooperating processes, or to a common mailbox. Message passing is for exchanging smaller amounts of data and is easier to implement.
        • Message passing is particularly useful in distributed environments, where the communicating processes may reside on different computers connected via a network.
        • A message passing facility provides at least two operations: send() and receive(). Messages sent by a process can be either fixed or variable in size.
        • Processes that want to communicate with one another must have a way to refer to each other. They can use either direct or indirect communication:
          1. Direct Communication: Each process that wants to communicate must explicitly name the recipient or sender of the communication. A communication link in this scheme is established automatically between every pair of processes that wish to communicate. Additionally, each link is associated with exactly two processes, and between each pair of processes, there exists exactly one link. This scheme exhibits symmetry in addressing. That is, both the sender and the receiver must name the other to communicate. Alternatively, in an asymmetric, only the sender names the recipient. The PID of the process is sent along with the message to the recipient.
          2. Indirect Communication: Messages are sent to and received from mailboxes/ports. A process can communicate with another via a number of different mailboxes, but two processes can communicate only if they have a shared mailbox. In this scheme, a communication link is established between a pair of process only if they have a shared mailbox. Furthermore, a link may be associated with more than two processes, and there may be a number of different ports between a pair of communicating processes. The mailbox may be owned by either a process or the OS.
        • Message passing may be either blocking or nonblocking:
          1. Blocking: The send/receive primitives block when called until the message is either successfully sent or received, respectively.
          2. Nonblocking: The send/receive is called, and execution continues as normal, without waiting.
        • Whether communication is direct or indirect, messages exchanged by communicating processes are placed in a temporary queue. Such queues can be implemented as:
          1. Zero Capacity: The queue has a maximum length of 0. In other words, the link cannot have any messages waiting in it. Therefore, the sender must block until the recipient receives the message.
          2. Bounded Capacity: The queue has a finite length. If the queue is full when the sender tries to send, the sender must block until space becomes available.
          3. Unbounded Capacity: The queue's length is potentially infinite, therefore, the sender never blocks.
    • The processes are responsible for ensuring mutual exclusion. The producer-consumer problem is a common problem for illustrating the importance of mutual exclusion. A producer produces information which the consumer consumes. This can also be interpreted as a metaphor for the client-server paradigm. One solution for the producer-consumer problem uses shared memory.
      • To allow the producer and consumer processes to run concurrently, we must have available a buffer of items that can be filled by the producer and emptied by the consumer. The producer and consumer must be synchronized, so that the consumer does not try to consume an item that has yet to be produced.
      • Two types of buffers can be used: an unbounded buffer places no limit on the size of the buffer, unlike a bounded buffer which can hold a fixed maximum number of items. If a bounded buffer is used, the producer must wait if the buffer is full, and the consumer must wait if the buffer is empty.
    • Pipes were one of the first IPC mechanisms in early UNIX systems.
      • Four issues must be considered when implementing a pipe:
        1. Is the pipe bidirectional or unidirectional?
        2. If two-way communication is allowed, is it half-duplex (data can travel only one way at a time) or full-duplex (data can travel in both directions simultaneously)?
        3. Must a relationship (such as parent/child) exist between the communicating processes?
        4. Can the pipes communicate over the network, or must the processes reside on the same machine?
      • Two common pipe implementations in UNIX include ordinary and named pipes:
        1. Ordinary Pipes: Allow two processes to communicate in the classic producer-consumer model: the producer writes to the write end of the pipe, and the consumer reads from the read end. Therefore, ordinary pipes are unidirectional, and if bidirectional communication is needed, two pipes must be used.
          • In UNIX systems, pipes are created with the pipe(int fd[]) function. The function creates a pipe that is accessed through the int fd[] file descriptors: fd[0] is the read-end of the pipe, and fd[1] is the write-end. Since pipes are treated as a special type of file, they can be accessed using ordinary read() and write() system calls.
          • An ordinary pipe cannot be accessed from outside the process that created it. Typically, a parent process creates a pipe and uses it to communicate with one of its children. Since a child inherits open files from its parent, and since the pipe is a special type of file, children inherit pipes from their parents. Furthermore, since ordinary pipes require a parent/child relationship, they cannot be used to communicate with processes on other machines.
          • Ordinary pipes
        2. Named Pipes: Permits bidirectional communication, without necessitating a parent/child relationship among communicating processes. Once a named pipe is established, several processes can use it for communication. Furthermore, named pipes continue to exist after communicating processes are finished.
          • In UNIX, named pipes are typically referred to as FIFOs (first-in first-outs). Once created, they appear as typical files in the file system. A FIFO is created with the mkfifo() system call, and can then be manipulated with ordinary open(), read(), write(), and close() system calls. It will continue to exist until it is explicitly deleted.
          • FIFOs are half-duplex, meaning data can only travel in one direction at a time. The communicating processes must also reside on the same machine. If inter-machine communication is required on a UNIX system, sockets must be used.
    • A socket is an endpoint for communication between processes. A pair of processes communicating across a network use a pair of sockets.
      • A socket is identified by an IP address concatenated with a port number. Generally, sockets adhere to a client-server architecture.
      • Servers implementing specific services listen to well-known ports. All ports less than 1024 are considered well-known, such as:
        • SSH: Port 22.
        • DNS: Port 53.
        • HTTP: Port 80.
        • HTTPS: Port 443.
        • FTP: Port 21.
      • When a client initiates a request for a connection, its host machine assigns it a port number. All connections must be unique.
      • The IP address 127.0.0.1 is known as the loopback address. That is, when a computer refers to IP address 127.0.0.1, it is actually referring to itself.
        • Communication between sockets is considered a low-level form of communication between distributed processes. One reason is that sockets only allow an unstructured stream of bytes to be changed between processes, and it is up to the client or server application to impose a structure on the data.
    • One of the most common forms of remote service is the remote procedure call (RPC) paradigm.
      • Unlike sockets, messages exchanged in RPC communication are well structured. Each message is addressed to an RPC daemon listening to a port on the remote system, and each contains an identifier specifying the function to executed and the parameters to be passed to that function. The function is then executed on the remote machine, and any output is sent back to the requester in a separate message. A port in the context of RPCs is simply a number included at the start of a message packet.
      • RPCs allow a client to invoke a procedure on a remote host as it would invoke a procedure locally. The RPC abstracts of this communication by providing a stub to the client. Typically, a separate stub is provided for each separate remote procedure.
      • When the client calls a remote procedure, the RPC system calls the corresponding stub, passing the provided parameters. This stub locates the port on the server and marshals the parameters. The stub then transmits a message to the server using message passing. A similar stub on the server side receives the message and invokes the requested procedure. Return values are passed back to the client using the same technique if necessary.
      • Parameter marshaling addresses differences in data representation on the client and server machines.
      • RPCs can fail, be duplicated and executed more than once, as a result of common network errors. Attaching a timestamp to each message can prevent repeated messages getting executed by comparing the timestamp of the message to that of recently executed messages. Incoming messages that have a timestamp already in the history are simply ignored. This ensures that the messages are acted on at most once. To ensure that the server does receive the request exactly once, we must remove the risk that the server never receives the request. This can be done by having the server send an acknowledgement message back to the client once the RPC call is received and executed. The client then re-sends each RPC call periodically until it receives an ACK message for that call.
      • The RPC scheme requires a binding of the client and server port. For the client to identify the appropriate server port, two common methods are employed:
        1. The binding information may be predetermined, in the form of a fixed port address. At compile time, an RPC call has a fixed port number associated with it.
        2. Binding can done dynamically by a rendezvous mechanism (*called a matchmaker*) daemon on a fixed RPC port. The client sends a message containing the name of the RPC it needs to execute to the matchmaker, which returns the associated port number.
      • The RPC scheme is useful for implementing distributed file systems (DFSs). Furthermore, RPCs can be used as a form of IPC between processes running on the same machine.

Ch.4 Threads & Concurrency

  • Virtually all modern operating systems provide features that enable a process to have multiple threads of execution. Identifying opportunities for parallelism through the use of threads is becoming increasingly important for creating high-performance applications, especially on multicore systems.

    • A thread is the basic unit of CPU utilization. It's made up of a thread ID, a program counter (PC), a register set, and a stack. It shares with other threads from the same process its code section, data section, and other OS resources such as open files and signals.
    • If a process is multithreaded, that is, has multiple threads of control, it can perform more than one task at a time. This is in contrast to a singlethreaded application, which must run sequentially. Most modern OS kernels are multithreaded.
    • Multithreading is especially useful for server applications. This can be done by employing one thread to listen to client requests. Whenever the server receives a request, it creates a thread to service that request, allowing it to continue to listen for additional requests. This approach is significantly faster since there is considerably less overhead for creating new threads than creating new processes. Many sorting, tree, and graph algorithms can be rewritten to take advantage of multithreading as well.
    • There are four main benefits of multithreaded programming:
      1. Responsiveness: Multithreading an interactive application enables a program to continue running, even in the face of blocked or lengthy operations. This is an especially useful quality for designing user interfaces (UIs).
      2. Resource Sharing: Processes share resources only through techniques such as shared memory or message passing. Threads, on the other hand, share the memory and resources of the process to which they belong to by default.
      3. Economy: Allocating memory and resources for process creating is costly. Since threads share the resources of the process to which they belong, it is more efficient and economical to create and context-switch threads.
      4. Scalability: The benefits of multithreading are especially evident on multiprocessor systems, where threads may be running in parallel on different processing cores.
    • On a system with a single core, concurrency means that the execution of threads will be tightly interleaved. On multicore systems, on the other hand, concurrency means that some threads run in parallel.

  • Modifying programs to take advantage of multithreading on multicore systems is a major challenge for application programmers.

    • Five areas present challenges in programming for multicore systems:
      1. Identifying Tasks: Examining applications to find areas that can be divided into separate, concurrent tasks. Tasks that are independent of one another are eligible to run in parallel across multiple cores.
      2. Balance: Programmers must ensure that each parallel task performs equal work of equal value to maximize the benefits of parallelism.
      3. Data Splitting: Just as applications are divided into separate tasks, the data accessed and manipulated by the tasks must be divided to run on separate cores.
      4. Data Dependency: Data accessed by parallel threads must be analyzed for dependencies. When one task relies on data from another, the programmer must ensure that the tasks are synchronized.
      5. Testing & Debugging: Multithreaded programs enable many different paths of execution, even when given the same inputs. This makes it significantly more difficult to test and debug such programs.

  • There are two types of parallelism:

    1. Data Parallelism: Distributing subsets of the same data across multiple cores and performing the same operation on each core.
    2. Task Parallelism: Distributing tasks (threads) across multiple computing cores.

  • Support for threads may be provided at either the user level, or the kernel level.

    • User threads are managed without kernel support. A relationship must exist between user threads and kernel threads. There are three common ways to establish such a relationship:
      1. Many-to-One Model: Maps many user-level threads to one kernel thread. Thread management is done by the thread library in user space, so it is efficient. However, the entire process will block if a thread makes a blocking system call. Furthermore, since only one thread can access the kernel at a time, multiple threads cannot run in parallel across multiple cores. Very few systems use this model because of its inability to take advantage of multicore systems.
      2. One-to-One model: Maps each user thread to a kernel thread. This model allows another thread to run if a thread makes a blocking system call, and allows multiple threads to run in parallel on different cores. The primary drawback is that creating a user thread requires creating the corresponding kernel thread, which may hinder performance. This model is used by both Linux and Windows.
      3. Many-to-Many Model: Multiplexes many user-level threads to a smaller or equal number of kernel threads. This model retains the parallelism of the one-to-one model, without the overhead of each each user thread having a corresponding kernel thread. Though, the many-to-many model is the most difficult model to implement. Furthermore, limiting the number of kernel threads is becoming less important as the number of processing cores increases.

  • A thread library provides the programmer with an API for creating and managing threads.

    • There are two primary ways to implement a thread library:
      1. Provide a library entirely in user space with no kernel support.
      2. Implement a kernel-level library supported directly by the OS. Invoking a function in the API for the library typically results in a system call to the kernel.
    • Three main thread libraries are in use today:
      1. POSIX Pthreads: The thread extension of the POSIX standard, which may be provided as either a user-level or a kernel-level library.
      2. Windows: A kernel-level library available on Windows systems.
      3. Java: Allows threads to be created and managed directly in Java programs. Though, since in most instances the JVM is running on top of a host OS, the Java thread API is typically implemented using a thread library available on the host system.
    • For Pthreads and Windows threading, any data declared globally is shared among all threads belonging to the same process. Since Java has no notion of global data, access to shared data must be explicitly arranged.

  • Two general strategies exist for creating multiple threads:

    1. Asynchronous Threading: Once the parent creates the child thread, the parent resumes its execution, allowing them to executed concurrently. There is typically little data sharing between threads. This is commonly used in multithreaded servers and responsive UIs.
    2. Synchronous Threading: The parent thread creates one or more children threads and then must wait until all of its children terminate before continuing. The children threads can executed concurrently, and only after all the children have joined can the parent resume execution. Typically, synchronous threading involves significant data sharing among threads.

  • Pthreads refers to the POSIX standard defining an API for thread creating and synchronization. Numerous systems implement the Pthreads specification, including Linux and MacOS.

    • In a Pthreads program, separate threads begin execution in a specified function.
    • All Pthreads programs must include the pthread.h header file. Each thread has a set of attributes, including stack size and scheduling information. Threads are of datatype pthread_t, which is used to uniquely identify the thread.
    • The pthread_attr_t datatype is used to store these attributes. The pthread_attr_init() function can be used to initialize the attributes.
    • Threads are created using the pthread_create() function. This function takes as arguments a pointer to a pthread_t variable, a pointer to a pthread_attr_t variable for the attributes, and a function pointer where the thread will begin execution.
    • The parent thread can wait for its child to terminate by calling the pthread_join() function. The child thread terminates by calling the pthread_exit() function. This is known as the fork-join model.

  • Implicit threading transfers the creation and management of threads from application programmers to compilers and run-time libraries.

    • This generally requires application programmers to identify tasks that can run in parallel. A task is usually written as a function, which the runtime library then maps to a separate thread, typically using a many-to-many model.

    • A multithreaded server, as described previously, has many potential problems. These include the amount of time required to make a thread after receiving a request, as well as the fact that the thread will be discarded after the request has been serviced. Furthermore, if we allow each concurrent request to be serviced with a new thread, we place no bound on the number of concurrent threads running on the system. One solution to this problem is a thread pool.

      • The idea behind thread pools is to create a number of threads at start-up and place them into a pool, where they wait to be assigned a task. When a server receives a request, rather than creating a thread, it submits a request to the thread pool and resumes waiting for additional requests. If there is a free thread in the pool, it is awakened, and the request is serviced immediately. Otherwise, the task is queued until a thread becomes available.
      • Thread pools offer the following benefits:
        1. Serving a request with a existing thread is often faster than creating a thread.
        2. A thread pool bounds the number of threads that can exist at any one point.
        3. Separating the task to be performed from the mechanics of creating the task allow us to use different strategies for running the task. For example, the task can be scheduled to execute after a time delay or to execute periodically.
      • More sophisticated thread pool architectures can dynamically adjust the number of threads in the pool according to usage patterns.

    • OpenMP is a set of compiler directives, as well as an API for programs written in C/C++ or FORTRAN that provides support for parallel programming in shared-memory environments.

      • OpenMP identifies parallel regions as blocks of code that may run in parallel. Application developers insert compiler directives into the source code at parallel regions, and these directives instruct the OpenMP runtime library to execute the region in parallel.
      • The OpenMP API is accessed through the omp.h header file.

  • Grand Central Dispatch (GCD) is a technology developed by Apple for its MacOS and iOS operating systems. It is a combination of a runtime library, an API, and language extensions that allow developers to identify sections of code (tasks) to run in parallel.

    • GCD schedules tasks for runtime execution by placing them on a dispatch queue . When it removes a task from the queue, it assigns the task to a free thread from a thread pool it manages.
    • GCD identifies two types of dispatch queues: serial and concurrent:
      • Tasks placed on a serial queue are removed in FIFO order. Once a task is removed from the queue, it must complete execution before another task is removed. Each process has its own serial queue (*known as its main queue*), and developers can create additional serial queues which are local to a particular process.
      • Tasks placed on a concurrent queue are also removed in FIFO order, but several tasks can be removed at once, allowing multiple tasks to execute in parallel.
    • Internally, GDC's thread pool is composed of POSIX Pthreads.

  • Intel threading building blocks (TBB) is a template library that support designing parallel applications in C++. Since it is a library, no proprietary compiler or language support is necessary. Developers specify tasks that can run in parallel, and the TBB task scheduler maps these tasks onto underlying threads.

    • The task scheduler also provides load balancing and is cache aware, meaning that it will give precedence to tasks that likely already have their data stored in cache memory.
    • Intel TBB has both commercial and open-source versions that can run on Windows, Linux, and MacOS.

  • The semantics of the fork() and exec() system calls can change in the context of a multithreaded program.

    • Some UNIX systems have two versions of fork(), one that duplicates all threads and another that duplicates only the thread that invoked fork().
    • The exec() system call typically works in the same way described earlier. That is, if a thread invokes exec(), the program specified in the parameter to exex() will replace the entire process, including all threads.
    • If exec() is called immediately after forking, then duplicating all threads is unnecessary. In this case, duplicating only the calling thread is appropriate. Though, if the separate process does not call exec() after forking, the separate process should duplicate all threads.

  • A signal is used in UNIX systems to notify a process that a specific event has occurred. A signal may be received either synchronously or asynchronously.

    • All signals follow the same pattern:
      1. A signal is generated by the occurrence of a specific event.
      2. The signal is delivered to a process.
      3. Once delivered, the signal must be handled.
    • Examples of synchronous signals include illegal memory accesses and division by 0. Synchronous signals are called synchronous because they are delivered to the same process that performed the operation that caused the signal.
    • When a signal is generated by an event that is external to a running process, that process receives the signal asynchronously. Typically, an asynchronous signal is sent to another process.
    • A signal may be handled by one of two handlers:
      1. The default signal handler.
      2. A user-defined signal handler.
    • Delivering signals in multithreaded programs is more complex because it requires identifying the correct thread to which the signal should be sent. In general, the following options exist:
      1. Deliver the signal to the thread to which it applies.
      2. Deliver the signal to all threads in the process.
      3. Deliver the signal to certain threads in the process.
      4. Assign a specific thread to receive all signals for the process.
    • The method for delivering a signal depends on the type of signal generated. Synchronous signals, for example, should be sent to the thread causing the signal only. Some asynchronous signals however, such as a signal that terminates a process, should be sent to all threads.
    • The UNIX function for delivering a signal is:
      • kill(pid_t pid, int signal)
    • Windows emulates signals using asynchronous procedure calls (APCs). The APC facility enables a user thread to specify a function that is to be called when the user thread receives a notification of a particular event.

  • Thread cancellation involves terminating a thread before it has completed.

    • A thread that is to be cancelled is referred to as the target thread. Thread cancellation may occur in two scenarios:
      1. Asynchronous Cancellation: One thread immediately terminates the target thread.
      2. Deferred Cancellation: The target thread periodically checks whether it should terminate, allowing it to terminate itself in an orderly fashion.
    • Thread cancellation incurs certain difficulties in situations where resources have been allocated to a cancelled thread or where a thread is cancelled while updating data it is sharing with other threads. This is especially troublesome with asynchronous cancellation.
    • In Pthreads, thread cancellation is initiated with the pthread_cancel() function. The thread identifier of the target thread is passed as a parameter. Invoking pthread_cancel() indicates only a request to cancel the target thread; actual cancellation depends on how the target thread is set up to handle the request. When the target thread finally cancels, the call to pthread_join() in the cancelling thread returns.
    • Pthreads allows threads to disable or enable cancellation. A thread with cancellation disabled cannot be cancelled, though, any cancellation requests remain pending. Therefore, if the thread enables cancellation later, it can still respond to the request.
    • Pthreads supports three cancellation modes. The default mode is deferred cancellation. In this scenario, cancellation only occurs when a thread reaches a cancellation point. Most of the blocking system calls in the POSIX and C standard library are defined as cancellation points.
      • One technique for establishing a cancellation point is to invoke the pthread_testcancel() function. If a cancellation request is found to be pending, the call will not return and the thread will terminate; otherwise, the call to the function returns and the thread continues to run.
      • Pthreads also allows a cleanup handler function to be invoked if a thread is cancelled. The function allows any resources that a thread may have acquired to be released before the thread terminates.
    • Asynchronous cancellation is not recommended in the Pthreads documentation because of the issues described earlier.
    • Thread cancellation in Java uses a policy similar to deferred cancellation in Pthreads.

  • Threads share the data of the process they belong to. Though, each thread may need its own copy of certain data. Such data is referred to as thread-local storage (TLS).

    • TLS is distinct from local variables in that local variables are visible only during a single function invocation, whereas TLS data are visible across function invocations.
    • TLS is also distinct from static data in that TLS data are unique to each thread.
    • Pthreads includes the pthread_key_t datatype, which provides a key that is specific to each thread. This key can then be used to access TLS data.
    • The gcc compiler provides the storage class keyword __thread for declaring TLS data.

  • Communication between the kernel and the thread library may be required by the many-to-many and two-level threading models. Such coordination allows the number of kernel threads to be dynamically adjusted to ensure the best performance.

    • Many systems implementing either the many-to-many or the two-level model place an intermediate data structure between the user and kernel threads. This data structure, known as a lightweight process (LWP) appears to the user-thread library as a virtual processor on which the application can scheduler a user thread to run. Each LWP is attached to a kernel thread, and it is kernel threads that the OS schedules to run on the actual CPU. If a kernel thread blocks, the LWP block as well; therefore, the user-level thread attached to the LWP also blocks.
    • An application may require any number of LWPs to run efficiently. Typically, an LWP is required for each concurrent blocking system call.
    • One scheme for communication between the user-thread library and the kernel is known as scheduler activation. It works as follows:
      • The kernel provides an application with a set of LWPs (virtual processors), and the application can schedule user threads onto an available LWP. Furthermore, the kernel must inform an application about certain events. This procedure is known as an upcall. Upcalls are handled by the thread library with an upcall handler, and upcall handlers must run on a virtual processor.
      • One event that triggers an upcall occurs when an application thread is about to block. The kernel makes an upcall to the application informing it that a thread is about to block and identifying said thread. The kernel then allocates a new LWP to the application. The application runs an upcall handler on this new virtual processor, which saves the state of the blocking thread and relinquishes the LWP on which it is running. The upcall handler then schedules another thread that is eligible to run on the new virtual processor. When the event that the blocking thread was waiting for occurs, the kernel makes another upcall to the thread library informing it that the previously blocked thread is now eligible to run. The upcall handler for this event also requires a virtual processor, and the kernel may allocate a new one or preempt one of the user threads and run the upcall handler on its LWP. After marking the unblocked thread as eligible to run, the application schedules an eligible thread to run on an available LWP.

  • Linux provides the fork()system call with the traditional functionality of duplicating a process. Linux also provides the ability to create threads using the clone() system call. However, Linux does not formally distinguish between processes and threads, instead, using the term task when referring to a flow of control within a program.

    • When clone() is invoked, it is passed a set of flags that determine how much sharing is to take place between parent and child tasks. These flags include:
      • CLONE_FS: File-system information is shared,
      • CLONE_VM: The same memory space is shared.
      • CLONE_SIGHAND: Signal handlers are shared.
      • CLONE_FILES: The set of open files are shared.
    • If none of these flags are set when clone() is invoked, it results in functionality similar to that of the fork() system call.
    • The varying level of sharing is possible because of the way tasks are represented in the Linux kernel. A unique kernel data structure of the type struct task_struct exists for each task in the system. This data structure stores pointers to other data structures where task data is stored, such as the list of open files, signal-handling information, etc. When fork() is invoked, a new task is created, along with a copy of all the associated data structures of the parent process. When clone() is invoked, on the other hand, rather than copying all data structures, the new task points to the data structures of the parent task depending on the flags passed.

Ch.5 CPU Scheduling

  • CPU scheduling is the basis of multiprogrammed operating systems. By allowing the CPU to switch among processes, multiple processes can be made to appear to be running in parallel on a single processor.

    • On modern operating systems, it is kernel-level threads that are being scheduled, not processes. Though, the terms "process scheduling" and "thread scheduling" are often used interchangeably.
    • The objective of multiprogramming is to have some process running on the CPU at all times to maximize CPU utilization. A process is executed until it must wait, typically for the completion of an I/O request. When the process must wait, the OS allocates the CPU to another process which is ready to run.
    • Process execution typically consists of cycles of CPU execution and I/O wait. These cycles are referred to as CPU bursts and I/O bursts. An I/O-bound program typically has many short CPU bursts. A CPU-bound program, on the other hand, may have few long CPU bursts.

  • When the CPU becomes idle, the OS is responsible for selecting one of the processes in the ready queue to be executed. This selection process is carried out by the CPU scheduler.

    • The ready queue is not necessarily a FIFO queue; typically, its implemented as some form of priority queue. Each record in the queue is generally a process control block (PCB) for the process.
    • CPU scheduling decisions take place under the following four circumstances:
      1. When a process switches from the running state to the waiting state. This typically occurs as the result of an I/O request or when waiting for a signal.
      2. When a process switches from the running state to the ready state, such as when an interrupt occurs.
      3. When a process switches from the waiting state to the ready state. For example, on the completion of an I/O request.
      4. When a process terminates.
    • For situations 1 and 4, there is no choice in terms of scheduling; a new process, if one exists, must be selected for execution. There is a choice, however, for situations 3 and 4.
    • When scheduling decisions take place only under circumstances 1 and 4, we say that the scheduling scheme is nonpreemptive, otherwise, it is preemptive.
      • Under nonpreemptive scheduling, when a process is allocated the CPU, it keeps the CPU until it voluntarily releases it either by terminating or by switching to the waiting state.
      • Virtually all modern operating systems use preemptive scheduling. Though, preemptive scheduling can result in race conditions when data are shared among multiple processes. For example, if one process is updating shared data and gets preempted, the data will be left in an inconsistent state. If another process attempts to read that data, it will get an incorrect value.
      • Additionally, operating system kernels can be designed as either preemptive or nonpreemptive themselves. A nonpreemptive kernel will wait for a system call to complete or for a process to block while waiting for I/O to complete to take place before doing a context switch. Though, this kernel-execution model is a poor one for supporting real-time computing, where tasks must complete execution within a given time frame. A preemptive kernel requires mechanisms such as mutex locks to prevent race conditions when accessing shared kernel data structures. Most modern operating systems are now fully preemptive when running in kernel mode.
    • Because interrupts can occur at any time, and because they cannot always be ignored by the kernel, the sections of code affected by interrupts must be guarded from simultaneous use. The OS needs to accept interrupts at almost all times. So that these sections of code are not accessed concurrently by multiple processes, they disable interrupts at entry and re-enable interrupts at exit.

  • Another component involved in CPU scheduling is the dispatcher.

    • The dispatcher is the module that gives control of the CPU's core to the process selected by the scheduler. This function involves the following:
      • Switching context from one process to another.
      • Switching to user mode.
      • Jumping to the proper location in the user program to resume that program.
    • The dispatcher should be fast, since it is invoked during every context switch. The time it takes for the dispatcher to stop one process and start another is known as the dispatch latency.
    • There are two types of context switches:
      1. Voluntary Context Switch: Occurs when a process has given up control of the CPU because it requires a resource that is currently unavailable.
      2. Nonvoluntary Context Switch: Occurs when the CPU has been taken away from a process, such as when its time quantum has expired, or its been preempted by a higher priority process.

  • Different CPU-scheduling algorithms have different properties, and may favor one class of processes over another.

    • Criteria for comparing CPU-scheduling algorithms include:
      1. CPU Utilization: We want to keep the CPU as busy as possible. CPU utilization ranges from 0 to 100 percent.
      2. Throughput: Can be measured as the number of processes completed per time unit.
      3. Turnaround Time: From the point of view of a particular process, the important criteria is how long it takes to execute that process to completion. Turnaround time is the sum of the periods spend waiting in the ready queue, executing on the CPU, and performing I/O.
      4. Waiting Time: Since the CPU-scheduling algorithm has no affect on the amount of time a process executes or does I/O, waiting time counts only the time spent waiting in the ready queue for a particular process.
      5. Response Time: The time from the submission of a request until the first response is produced. This is the time it takes to start responding, not the time it takes to output the response.
    • It is desirable to maximize CPU utilization and throughput and to minimize turnaround, waiting, and response time. In most cases, we optimize the average measure. Though, under some circumstances, we prefer to optimize the maximum or minimum values.

  • Common CPU-scheduling algorithms include :

    • First-Come First-Serve (FCFS): This is the simplest scheduling algorithm which schedules processes/threads in the order that they arrive. This algorithm is implemented with a FIFO queue. The average waiting time under FCFS is generally not minimal. For example, if a CPU-bound process is scheduled to run before multiple I/O-bound processes, the I/O-bound processes would wait a long time for the CPU-bound process to execute. A better alternative would be to let the I/O-bound processes execute first, since they are likely to block very quickly.
      • Furthermore, FCFS is nonpreemptive; that is, once the CPU has been allocated to a process, that process keeps the CPU until it either blocks, or requests I/O.
    • Shortest-Job-First (SJF): This algorithm associates with each process the length of its next CPU burst. The algorithm then allocates the CPU to the ready processes in the order of increasing CPU burst length. This algorithm is provably optimal, in that it gives the minimum average waiting time for a given set of processes.
      • Although the SJF algorithm is optimal, it cannot be practically implemented since there is no way for the scheduler to know the length of the upcoming CPU bursts of processes. One approach is to try to approximate SJF by taking the exponential average of the measured length of previous CPU bursts.
      • The SJF algorithm can be either preemptive or nonpreemptive.
      • Since SJF is provably optimal, it is commonly used to compare other scheduling algorithms.
    • Round-Robin (RR): Similar to FCFS, but preemption is added to enable the system to switch between processes. A small unit of time, called the time quantum is defined. Such a time quantum is generally from 10 to 100 milliseconds in length. The ready queue is implemented as a circular FIFO queue. The CPU scheduler goes around the ready queue, allocating each process the CPU for up to 1 time quantum.
      • If the CPU burst of the currently running process is longer than 1 time quantum, the timer will go off and will cause an interrupt to the OS. A context switch will be executed and the process will be put at the end of the circular queue.
      • The average waiting time under RR is often long. Furthermore, the performance of the RR algorithm depends heavily on the size of the time quantum. If the time quantum is too large, the RR policy degenerates to a FCFS policy. Alternatively, if the quantum is too short, the RR approach can result in large amounts of overhead due to excessive context switches. Therefore, we want the quantum to be large with respect to the context switch time. A general rule of thumb is that 80 percent of the CPU bursts should be shorter than the time quantum.
    • Priority-Scheduling: The SJF policy is a special case of the more general priority-scheduling algorithm. Priorities are associated with each process, and processes are allocated the CPU in descending order of priorities. The SJF algorithm is a priority algorithm where the priority is the inverse of the length of the next CPU burst.
      • Priorities are generally indicated by some fixed range of numbers. In some systems, low numbers represent high priority, and in some cases, low numbers represent high priority.
      • Priorities can be defined internally or externally. Internally defined priorities are use some measurable quantity or quantities to compute the priority of a process. Such quantities may include time limits, memory requirements, the number of open files, etc. External priorities are set by criteria outside of the OS, such as the importance of a process, the department sponsoring the work, and other (often political) factors.
      • Priority scheduling can be either preemptive or nonpreemptive. A preemptive priority algorithm will preempt the currently running process is some newly arrived process has higher priority. A nonpreemptive priority algorithm, on the other hand, would put the new process on the head of the ready queue.
      • A major problem with priority algorithms is the possibility of starvation. Starvation occurs when some low priority process is ready to run, but is never allocated the CPU because there are always higher priority processes ready to run.
        • A solution to starvation is aging. That is, gradually increasing the priority of processes that wait in the system for a long time. Another option is to combine round-robin and priority scheduling in such a way that the system executes the highest-priority process, and runs processes with the same priority using round-robin scheduling.
    • Multilevel Queue Scheduling: With a single queue, an search may be necessary to determine which process is the highest priority process. One solution to this problem is to have a queue for each distinct priority level. The scheduler then simply schedules the processes in the highest-priority queue.
      • Typically, a multilevel queue scheduler is combined with a round-robin policy, so that processes in the same queue are executed in round-robin fashion.
      • A multilevel queue scheduler can also be used to partition processes into several separate queues based on process type, such as foreground and background processes. Furthermore, each queue may have its own scheduling algorithm.
      • There must also be scheduling among the queues themselves, which is commonly implemented as fixed-priority preemptive scheduling. Alternatively, the queues can be time-sliced, that is, each queue is given a certain portion of the CPU time, which it can then use to schedule among its various processes.
    • Multilevel Feedback Queue Scheduling: Generally, when a multilevel queue scheduler is used, processes are permanently assigned to a queue when they enter the system. The multilevel feedback queue scheduling algorithm, on the other hand, allows a process to dynamically move between queues.
      • The idea is to separate processes according to the characteristics of their CPU bursts. If a process uses too much CPU time, it is moved to a lower-priority queue. This leaves I/O bound and interactive processes in the higher-priority queues. Furthermore, processes that wait too long in lower priority queues can be promoted to prevent starvation.
      • A multilevel feedback queue scheduler may also assign different time quantums to each queue. Typically, higher-priority queues have a smaller time quantum, since the processes in these queues are typically I/O bound.
      • Generally, a multilevel feedback queue scheduler is defined by the following parameters:
        1. The number of queues.
        2. The scheduling algorithm for each queue.
        3. The method(s) used to determine when to promote a process to a higher-priority queue.
        4. The method(s) used to determine when to demote a process to a lower-priority queue.
        5. The method used to determine which queue a process will enter when that process requires service.

  • On most modern operating systems, it is kernel threads, not user-level threads, that are being scheduled by the OS. User-level threads are managed by a thread library, and the kernel is unaware of them.

    • The run on a CPU, user threads must be mapped to kernel threads, although this mapping may be indirect and may use a lightweight process (LWP).
    • On systems implementing the many-to-one and many-to-many thread models, the thread library schedules user threads to run on an available LWP. This scheme is known as process-contention scope (PCS), since competition for the CPU takes place among threads belonging to the same process.
      • Typically, PCS is done according to priority. User-level thread priorities are set by the programmer and not adjusted by the thread library.
    • The decide which kernel thread to schedule on to a real CPU, the kernel uses system-contention scope (SCS). Competition for the CPU with SCS scheduling takes place among all threads in the system. Systems implementing the one-to-one thread model (such as Windows and Linux) schedules threads using only SCS.

  • A multicore system adds significant complexity to scheduling due to the introduction of the load sharing problem. In such systems, it's essential to efficiently distribute workload across multiple cores to maximize performance and ensure that resources are utilized effectively.

    • Homogeneous systems are systems where all processors are identical in terms of their functionality.
    • One approach to multicore scheduling is to reserve all scheduling decisions, I/O processing, and other system activities for a single processing core, called the master server. The other processes execute only user code. This asymmetric multiprocessing is simple because only one core accesses system data structures, reducing the need for data sharing. Though, this approach allows the master server to become a potential bottleneck for overall system performance.
    • The standard approach for supporting multiprocessors is symmetric multiprocessing (SMP), where each processor is self-scheduling. Scheduling proceeds by having the scheduler for each processor examine the ready queue and select a thread to run. This provides two possible strategies for organizing the ready threads:
      1. All threads may be in a common ready queue. This creates possible race conditions if two processors select the same thread simultaneously. We could use some form of locking to protect the common ready queue, though, locking will be highly contended as all accesses to the ready queue will require lock ownership.
      2. Each processor may have its own private ready queue. This is the most common approach on SMP systems. Private ready queues may also lead to more efficient use of cache memory. Though, the main drawback of such an approach is load balancing; though, balancing algorithms exist to equalize the workloads among all processors.
    • When processor accesses memory, it spends a significant amount of time waiting for that memory to become ready, such a situation is referred to as a memory stall. This occurs primarily because modern processors run at much faster speeds than memory. However, memory stalls can also occur as the result of a cache miss.
    • Recent hardware designs have implemented multithreaded processor cores in which two or more hardware threads are assigned to each core. That way, if one hardware thread stalls as a result of a memory access, the core can switch to another thread.
    • From an OS perspective, each hardware thread maintains its architectural state, such as its program counter (PC) and register set, and thus appears as a logical CPU that is available to run a software thread. This technique is known as chip multithreading (CMT). Intel processors use the term hyperthreading or simultaneous multithreading (SMT) to describe assigning multiple hardware threads to a single processing core.
      • In general, there are two ways to multithread a processing core:
        1. Coarse-Grained: A thread executes on a core until a long-latency event such as a memory stall occurs. The core then switches to another thread. The cost of thread switching is high, since the instruction pipeline must be flushed before the other thread can begin executing.
        2. Fine-Grained: Switches between threads at a fine level of granularity, typically at the boundary of an instruction cycle. The architectural design of fine-grained systems include logic for thread switching. As a result, the cost of switching between threads is small.
      • The hardware resources of the physical core (such as caches and pipelines) must be shared among its hardware threads; therefore, a processing core can execute only one thread at a time.
      • A multithreaded, multicore processor requires two levels of scheduling:
        1. On one level are the scheduling decisions made by the OS as it chooses which software thread to run on each hardware thread (logical CPU).
        2. A second level of scheduling specifies how each core decides which hardware thread to run.

  • On SMP systems, it is important to keep the workload balanced among all processors, a problem known as load balancing.

    • Load balancing is typically necessary on systems where each processor has its own private ready queue.
    • There are two general approaches to load balancing:
      1. Push Migration: A specific task periodically checks the load on each processor. If it finds an imbalance, it balances the load by pushing threads from overloaded to underloaded cores.
      2. Pull Migration: Occurs when an idle processor pulls a waiting task from a busy processor.
    • Push and pull migration are often implemented in parallel on load-balancing systems.

  • When a thread runs on a CPU, the most recently accessed data is going populate the cache for that processor. As a result, successive memory accesses by the thread are often satisfied by cache memory. This situation is known as a warm cache.

    • If the thread migrates to another processor, say due to load balancing, the contents of cache memory must be invalidated for the first processor, and the contents of the cache of the second processor must be repopulated. Because of the high cost of invalidating and repopulating caches, most operating systems try to keep threads running on the same processor, a technique known as processor affinity.
    • With a global ready queue, a thread may be selected for execution by any processor. With private, per-processor ready queues, on the other hand, a thread is always scheduled on the same processor and can therefore reap the benefits of a warm cache. Essentially, pre-processor ready queues implement processor affinity for free.
    • When an OS has a policy of attempting to keep a process running on the same processor, but not guaranteeing that it will do so, the OS implements soft affinity. Hard affinity, on the other hand, allow a process to specify a subset of processors on which it can run. Many systems provide both soft and hard affinity.
    • The architecture of main memory can also affect processor affinity issues. A non-uniform memory access (NUMA) architecture is a memory design used in multiprocessor systems, where the access time to memory varies depending on the location of the memory relative to a processor. Although a system interconnect allows all CPUs in a NUMA system to share one physical address space, a CPU has faster access to its local memory than to memory local to another CPU. If the OS's scheduler and memory-placement algorithms are NUMA-aware, then a thread that has been scheduled on a CPU can be allocated memory closest to where the CPU resides.
    • Load balancing often counteracts the benefits of processor affinity. Furthermore, migrating a thread between processors may incur a penalty on NUMA systems, where a thread may be moved to a processor that requires longer memory access times. Therefore, there is a natural tension between load balancing and minimizing memory access times.

  • Many mobile systems now include multicore architectures, though, each core may vary in terms of its clock speed and power management. Such systems are known as heterogeneous multiprocessing (HMP).

    • The intention behind HMP is to mange power consumption by assigning tasks to certain cores based upon the specific demands of the task. For ARM processors, this architecture is known as big.LITTLE where high-performance big cores are combined with energy efficient LITTLE cores.
    • A CPU scheduler can assign tasks that don't require high performance, but may need to run for longer periods, to little cores, thereby preserving battery charge.
    • Furthermore, if the mobile device is in power-saving mode, energy-intensive big cores can be disabled entirely and the system can rely solely on energy-efficient little cores.

  • CPU scheduling for real-time operating systems (RTOS) introduce special issues.

    • Soft real-time systems provide no guarantee as to when a critical real-time process will be scheduled. They guarantee only that the process will be given priority over noncritical processes. In hard real-time systems, on the other hand, a task must be serviced by its deadline. Service after the deadline is the same as no service at all.
    • Real-time systems are typically event-driven. Events may arise in software, such as when a timer expires, or in hardware, such as when a sensor detects an object. Event latency is the amount of time that elapses from when an even occurs to when it is serviced.
    • Two types of latencies affect the performance of real-time systems:
      1. Interrupt Latency: The period of time from the arrival of an interrupt at the CPU to the start of the interrupt service routine (ISR). The interrupt latency includes the time it takes for the OS to finish the instruction it is currently executing, determine the type of the interrupt, save the state of the current process, and service the interrupt using the corresponding ISR. For hard real-time systems, interrupt latency must not simply be minimized, it must be bounded.
        • Interrupt latency also includes the amount of time that interrupts may be disabled while kernel data structures are being updated. Hard real-time systems require that interrupts be disabled for only short periods of time.
      2. Dispatch Latency: The amount of time required for the scheduling dispatcher to stop one process and start another. The most effective technique for keeping dispatch latency low is to provide preemptive kernels.
      • The most important factor of a RTOS is to respond immediately to real-time processes as soon as such a process requires the CPU. Therefore, the scheduler for a RTOS must support a priority-based algorithm with preemption. Though, such a scheduler only guarantees soft real-time functionality. Hard real-time systems must guarantee that real-time tasks will be serviced before their deadlines.
      • Real-time processes are considered periodic. That is, they require the CPU at constant intervals. A process may have to announce its deadline requirements to the CPU scheduler. Then, using a technique called an admission-control algorithm, the scheduler does one of two things: it either admits the process, guaranteeing that it will complete on time, or it rejects the request as impossible to fulfill.
      • The rate-monotonic scheduling algorithm schedules periodic tasks using a static priority policy with preemption. Upon entering the system, each periodic task is assigned a priority inversely based on its period. The shorter the period, the higher the priority, and vice versa. The reasoning behind this is to assign a higher priority to tasks that will need the CPU more often.
        • Rate-monotonic scheduling also assumes that the processing time of a periodic process is the same for each CPU burst.
        • Rate-monotonic scheduling is considered optimal in the sense that if a set of processes cannot be scheduled by this algorithm, it cannot be scheduled by any other algorithm that assigns static priorities.

    • Earliest deadline first (EDF) scheduling assigns priorities dynamically according to the process's deadline. The earlier the deadline, the higher the priority. Under this policy, when a process becomes runnable, it must announce its deadline to requirements to the OS.
      • EDF scheduling does not require that processes be periodic, nor must a process require a constant amount of CPU time per CPU burst.
      • EDF is theoretically optimal; theoretically, it can schedule processes so that each process can meet its deadline requirements and CPU utilization will be 100 percent. In practice, however, it is impossible to achieve 100 percent CPU utilization due to the overhead of context switching and interrupt handling.
    • Proportional share schedulers allocate time shares among all applications. An application can receive shares, thus causing the application to be allocated of the total processor time.
      • Proportional share schedulers must work in conjunction with an admission-control policy to guarantee that an application receives its allocated shares of time. An admission-control policy will admit a client requesting a particular number of shares only if sufficient shares are available.

  • Since version 2.6, the Linux kernel uses a scheduler known as the Completely Fair Scheduler (CFS).

    • Scheduling in Linux is based on scheduling classes. Each class is assigned a specific priority. By using different scheduling classes, the kernel can accommodate different scheduling algorithms based on the needs of the system and its processes.
    • Standard Linux kernels implement two scheduling classes: a default scheduling class using the CFS scheduling algorithm, and a real-time scheduling class.
    • The CFS scheduler assigns a proportion of CPU time to each task. This proportion is based on the nice value assigned to each task. Nice values range from -20 to 19, where a numerically lower nice value indicates a higher relative priority. The default nice value is 0. Tasks with high nice values are considered nice to the other tasks in the system because they lower their own relative priority.
    • CFS doesn't use discrete values of time slices. Instead, it identifies a target latency, which is an interval of time during which each runnable task should run at least once. Proportions of CPU time are allocated from the value of the target latency. The targeted latency can increase if the number of active tasks in the system grows beyond a certain threshold.
    • The CFS scheduler doesn't directly assign priorities. Rather, it records how long each task has run by maintaining the virtual runtime of each task using the per-task variable vruntime. The virtual runtime is associated with a decay factor based on the priority of a task: lower-priority tasks have higher rates of decay than higher-priority tasks.
      • For tasks of normal priority (i.e., tasks with nice values of 0), virtual runtime is equivalent to actual runtime. For tasks with lower-priority, their vruntime will be higher than their physical runtime. For tasks with higher-priority, their vruntime will be lower than their physical runtime.
    • The decide which task to run next, the scheduler simply selects the task with the smallest vruntime value. Additionally, a higher-priority task that becomes available to run can preempt a lower-priority task.
    • Linux also implements real-time scheduling according to the POSIX standard. Any task scheduled with either the SCHED_FIFO or SCHED_RR real-time policy runs at a higher priority than normal tasks.
      • Real-time tasks are assigned static priorities within the range of 0-99, and normal tasks are assigned priorities from 100-139. These two ranges map into a global priority scheme where numerically lower values indicate higher relative priorities. Normal tasks are assigned priorities based on their nice values.
    • The CFS scheduler also supports load balancing, using a technique that is NUMA-aware and minimizes the migration of threads. CFS defines the load of each thread as a combination of the thread's priority and its average rate of CPU utilization.

  • When wanting to select a CPU-scheduling algorithm for a particular system, we must first define the criteria to be used in selecting an algorithm.

    • Criteria are often defined in terms of CPU utilization, response time, or throughput. Once the selection criteria have been defined, we want to evaluate the algorithms under consideration. Evaluation methods include:
      • Deterministic Modeling: Analytic evaluation uses the given algorithm and the system workload to produce a formula or number to evaluate the performance of the algorithm for that workload. Deterministic modeling is one type of analytic evaluation. This method takes a particular predetermined workload and defines the performance of each algorithm for that workload.
        • Deterministic modeling is simple and fast, though, it requires exact numbers for input, and its answers apply only to those cases. The main uses for deterministic evaluation are in describing algorithms and providing examples.
      • Queuing Models: On many systems, the processes that run vary from day to day. Though, we can determine the distribution of CPU and I/O bursts by either measuring or simply estimating. These result is a mathematical formula describing the probability of a particular CPU burst. It is common for the distribution to be exponential, and is typically described by its mean. Similarly, we can describe the arrival-time distribution; that is, the distribution of times when processes arrive in the system. From these two distributions it is possible to compute the average throughput, utilization, waiting time, and so on, for most algorithms.
        • The computer system is described as a network of servers. Each server has a queue of waiting processes. The CPU is a server with its ready queue, as is the I/O subsystem with its device queues. Ch.6 Synchronization Tools

  • A cooperating process is one that can affect or be affected by other processes executing in the system.

    • Cooperating processes can either directly share an address space, or be allowed to share data only through shared memory and message passing. Concurrent access to data may result in data inconsistency.
    • A process can be interrupted at any point in its instruction stream, and the processing core may be assigned to execute instructions of another process. Furthermore, two instruction streams (representing two separate threads) can be executing in parallel across multiple cores. Such conditions can lead to problems such as:
      1. Race Conditions: Occur when multiple processes/threads access shared data simultaneously, resulting in unpredictable results if one thread writes data while the other is reading it. Careful synchronization is required to prevent such situations.
        • Synchronization is commonly implemented using locks. A process that wants to write to a shared data resource must acquire this lock. Once the writing process obtains the lock, no other thread can access the shared data until the lock is released.
      2. Deadlocks: Occur when multiple threads are waiting indefinitely for a resource (typically a lock) held by another thread. Proper resource allocation strategies must be carried out to avoid deadlocks.
      3. Starvation: Occur when a process never gets a resource that it needs (such as a lock) to complete its execution because other processes are continuously prioritized over it.
    • The producer-consumer problem described in Chapter 3 is a common problem used to demonstrate synchronization requirements for cooperating processes. We described how a bounded buffer can be used to enable processes to share memory.
      • The bounded-buffer solution has a fixed-size buffer, which the producer stores data into, and the consumer reads data from. We could have a separate variable count, which stores the amount of data items currently in the buffer. If count == size(buffer) - 1, then the buffer must be full; if count == 0, then the buffer must be empty.
      • Whenever the producer writes to the buffer, it can also increment the count variable. Conversely, the consumer can decrement count whenever it reads from the buffer. The problem with this solution is that the count variable can be incremented and decremented simultaneously by the producer and consumer threads, respectively. Furthermore, either the producer or the consumer can be interrupted/preempted in between the instruction that writes/reads the buffer, and the instruction that increments/decrements the count variable. This can lead to incorrect and unpredictable results when executing the program concurrently.
        • A situation like this, where both processes can access and manipulate the same data simultaneously, and the outcome depends on the particular order in which the accesses take place, is an example of a race condition. To remedy this, we need to ensure that one process can manipulate the shared data at a time. Additionally, while one process is manipulating the data, no other process should be able to read the data until the writing process is finished.

  • Each cooperating process has a particular segment (or segments) of code which may access or update shared data. Such a segment of code is referred to as that process's critical section. The critical-section problem involves ensuring that no two processes can be in their critical section at the same time.

    • We must design and implement a protocol that enables processes to synchronize their activities so they can cooperatively share data. Each process must seek permission to enter its critical section; the section of code implementing this request is known as the entry section. The critical section may be followed by an exit section, with the remaining code being the remainder section.
    • A solution to the critical-section problem must satisfy the following requirements:
      1. Mutual Exclusion: If process is executing in its critical section, then no other process can be executing in their critical section.
      2. Progress: If no process is executing in its critical section and some processes wish to enter their critical sections, then only those processes that are not executing in their remainder sections can participate in deciding which will enter its critical section next, and this selection cannot be postponed indefinitely.
      3. Bounded Waiting: There exists a bound on the number of times that other processes are allowed to enter their critical sections after a process has made a request to enter its critical section before that request is granted.
    • The critical-section problem can be solved simply in a single-core system by preventing interrupts from occurring while a shared variable is being modified. Unfortunately, this solution is not feasible in a multiprocessor system since disabling interrupts on a multiprocessor can be time consuming, since the message must be passed to all processors.
    • Two general approaches exist for handling critical sections in operating systems:
      1. Preemptive Kernels: Allows a process to be preempted while it is running in kernel mode. Such kernels are especially difficult to design for SMP architectures, since in these environments it is possible for two kernel-mode processes to run simultaneously on different cores. Though, preemptive kernels may be more responsive, since there is less risk that a kernel-mode process will run for a long period of time. Furthermore, a preemptive kernel is more suitable for real-time programming, as it will allow a real-time process to preempt a process currently running in the kernel.
      2. Nonpreemptive Kernels: Does not allow processes in kernel to be preempted. Such a kernel is free from race conditions on kernel data structures.

  • Software-based solutions to the critical-section problem, such as Peterson's solution, are not guaranteed to work on modern computer architectures because of the way such architectures reorder machine instructions. Though, there exist hardware instructions that provide support for solving the critical-section problem. These primitive operations can be used directly as synchronization mechanisms, or they can be used to form the foundation of higher-level synchronization tools.

    • How a computer determines what memory guarantees it will provide to an application is known as its memory model. Generally, memory models fall into one of two categories:
      1. Strongly Ordered: A memory modification on one processor (core) is immediately visible to all other processors.
      2. Weakly Ordered: Memory modifications on one processor may not be visible to all other processors immediately.
    • Memory models vary by processor type, so kernel developers cannot make any assumptions regarding the visibility of modifications to memory on a shared-memory multiprocessor. To address this problem, computer architectures provide instructions that can force any changes in memory to be propagated to all other processors. Such instructions are known as memory barriers/fences.
      • When a memory barrier instruction is performed, the system ensures that all loads and stores are completed before any subsequent load or store operations are performed. Therefore, even if instructions were reordered, the memory barrier ensures that the store operations are completed in memory and visible to other processors before future memory operations.
    • Many modern architectures provide special instructions that enable a programmer to test and modify the content of a word, or to swap the contents of two words atomically, that is, in one uninterruptible operation. Such instructions may be referred to as the test_and_set and compare_and_swap instructions, respectively.
      • Such instructions can be used to implement mutual exclusion:
        • The test_and_set instruction be used to implement mutual exclusion by having a binary lock variable (lock) initialized to 0. The test_and_set instruction can be used change the value of the lock conditionally and atomically. If two cores were to attempt the change the value of lock simultaneously, since the instruction is atomic, one will certainly execute before the other. When a process exits its critical section, it sets lock back to 0, which enables another process to enter its critical section.
        • The compare_and_swap (CAS) instruction can also be used to implement mutual exclusion. A global variable (lock) is initialized to 0, the first process that invokes compare_and_swap will set the lock to 1. It will then enter its critical section because the original value of lock was equal to its expected value of 0. Subsequent calls to compare_and_swap will fail because lock is not equal to the expected value of 0. When a process exits its critical section, it sets lock back to 0, which enables another process to enter its critical section.
      • Although these algorithms satisfy the mutual exclusion requirement, they do not satisfy the bounded-waiting requirement.
      • Typically, the CAS instruction is not used directly to provide mutual exclusion. Rather, it is used as a basic building block for construction other synchronization tools, such as atomic variables. Atomic variables provide atomic operations on basic data types such as integers or Booleans. Most systems that support atomic variables provide special atomic data types as well as functions for accessing and manipulating such types. These functions are often implemented using CAS operations.
